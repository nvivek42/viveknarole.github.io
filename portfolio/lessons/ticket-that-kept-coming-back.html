The ticket that kept coming back.

On patterns nobody documented, and the system built to finally catch them.

Portfolio Lessons

Every IT team has a version of this. Slowness reported. Engineer opens a ticket. Checks CPU. Checks RAM. Closes it. Two weeks later — same machine, same complaint, different engineer, same manual walk-through. No record of what was tried. No memory between tickets. The pattern exists. The system just never had a way to see it.

Someone eventually has to get tired enough to build the thing that should have existed already. In this case, that person had an odd mix of backgrounds — engineering, psychology, years spent studying how systems and people break down — and no particularly clean reason to be the one doing it.

That turned out to matter more than expected.

Every detour quietly deposited something I didn't know I'd need.

Engineering

structured thinking → deterministic RCA chain. No guessing.

UPSC · Psychology

multiperspective reasoning → UX decisions a pure dev wouldn't make.

Failed interviews

narrow became wide → finally understood the full IT landscape.

All of it

persistence without proof → shipped anyway. Iterated until it worked.

Ticketing System didn't come from a clean career path. It came from watching an L1 engineer correlate the same failures for the fiftieth time — and recognising the pattern because I'd spent years learning how humans, systems, and organisations actually break down.

The self-doubt didn't disappear. I just stopped waiting for it to. Range isn't a strategy. It's what you have left when every safe option has already failed you.
