AI-Assisted Debugging Infrastructure

August 2025 6 weeks GitHub Live Demo — WIP
Python FastAPI ChromaDB Celery + Redis OpenTelemetry LLM Integration

The Problem

Debugging distributed systems is reactive, tribal, and slow. When an incident fires, on-call engineers: (1) grep logs across 10+ services, (2) correlate metrics manually, (3) recall similar past incidents from memory or Confluence, (4) piece together a hypothesis, (5) verify. Mean Time to Resolution (MTTR) is dominated by steps 1–3 — information gathering, not fixing.

Existing tools (Datadog, PagerDuty, Splunk) surface alerts but don't connect them to root cause patterns. Runbooks are static, outdated, and generic. The "senior engineer's intuition" is an unshared, unscalable asset.

Approach

Built a three-layer infrastructure that turns tribal knowledge into queryable, executable patterns:

  1. Pattern Library (RCA Corpus): Structured database of 200+ historical incidents — each with symptoms (logs, metrics, traces), root cause, contributing factors, resolution steps, and prevention. Stored as Markdown + YAML frontmatter, version-controlled, searchable.
  2. Signal Correlation Engine: Ingests OpenTelemetry traces, Prometheus metrics, and structured logs. Uses vector embeddings (sentence-transformers, 384-dim) to map incoming alert clusters to similar historical patterns. Rule engine (YAML-defined business logic + learned thresholds) filters noise and proposes candidate root causes with confidence scores.
  3. Runbook Generator: Given a matched pattern + current context (affected services, deployment status, recent changes), synthesizes a dynamic runbook: prioritized investigation steps, relevant dashboards, exact queries to run, escalation contacts, and rollback procedures.

Technical architecture:

  • Python 3.11+ async pipeline (FastAPI for ingestion, Celery + Redis for async correlation)
  • ChromaDB for vector storage (local, no external vector service)
  • Custom rule engine (YAML-defined, hot-reloadable)
  • LLM integration (local Ollama / remote API) for runbook synthesis and pattern extraction from postmortems
  • OpenTelemetry native — no vendor lock-in
Dependencies: Redis (Celery broker), PostgreSQL (metadata), ChromaDB (local vector store), Ollama or remote LLM API. Not "zero external services" — runs on-prem with standard infrastructure.
Design principle: AI proposes, human disposes. The system never auto-executes remediation. It reduces the search space from "everything" to "top 3 hypotheses with evidence."

Solution

A modular Python package (ai-debugging-infra) with CLI and API:

  • ingest — Parse postmortems (Notion, Confluence, Markdown) into pattern library
  • correlate — Real-time alert cluster → pattern matches (~1.5s p95)
  • runbook — Generate context-aware investigation guide (Markdown/HTML)
  • learn — Post-incident: feed resolution back into library (human-in-the-loop)

Deployable as sidecar, standalone service, or library. Integrates with PagerDuty, Slack, Grafana via webhooks. Public repo includes a sanitized sample corpus (synthetic incidents) for evaluation.

Impact & Metrics

Measured (on historical data)

78% Top-3 root-cause match
15 → 2 min First-actionable-query time
~200 Patterns in corpus
50 Services in test system

Test methodology: 3 months of historical incidents from a 50-service production environment. The test set was held out from the pattern library (incidents from month 3; library built from months 1–2). Correlation engine surfaced correct root cause in top-3 for 78% of held-out incidents. Walkthrough exercises (N=12 engineers, 6 scenarios) reduced "first actionable query" time from ~15 min to ~2 min.

Targets (not yet measured in production)

40% MTTR Reduction
<5% False Positive Rate
<2s Correlation Latency (p95)

What Went Wrong

  • Over-indexed on vector search initially. The first version used only embeddings. Precision was ~45%. Adding deterministic rule-based signatures (exact metric thresholds, log regexes) pushed it to 78% top-3. Lesson: structure beats semantics for operational patterns.
  • Didn't involve on-call engineers early enough. Built the matching engine in isolation. When demoed, engineers ignored it because it surfaced "obvious" matches they already knew. Added a "novelty score" — only show matches the current engineer hasn't seen — and engagement jumped.
  • Schema drift broke fingerprints silently. Monitoring metric names changed (e.g., cpu_usage → cpu.utilization) and fingerprints degraded without alerts. Added a schema registry with drift detection.
  • No offline fallback. When the correlation service was down, engineers had no fallback. Added a local cache of recent patterns in the UI widget.
  • Leakage risk in validation. The 200 patterns came from the same incident corpus. The held-out test (month 3 vs months 1–2) mitigates this, but temporal leakage (recurring patterns) remains possible. Need a proper temporal split with gap.
