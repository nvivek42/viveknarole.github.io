RCA Ticketing System

September 2024 6 weeks GitHub Confidential — screenshots on request
Python FastAPI PostgreSQL React Elasticsearch Docker

The Problem

In a large enterprise IT organization, L1/L2 support engineers repeatedly diagnosed the same incidents from scratch. A ticket for "server slowness" would arrive, an engineer would check CPU, RAM, disk, close it — and two weeks later the same machine, same complaint, different engineer, same manual walk-through. No record of what was tried. No memory between tickets.

The pattern existed. The system just never had a way to see it. Mean Time to Resolution (MTTR) was dominated by information gathering, not fixing. Institutional knowledge lived in engineers' heads and disappeared when they rotated.

Approach

Built a diagnostic memory layer on top of the existing ticketing workflow — not a replacement, an augmentation.

1. Automatic symptom extraction

When a ticket is created, the system pulls recent metrics (CPU, memory, disk, network), recent logs (error patterns, stack traces), and recent changes (deployments, config updates) from monitoring APIs. This becomes the "symptom fingerprint" — structured, searchable, attached to the ticket automatically.

2. Historical pattern matching

The fingerprint is matched against past incidents using a combination of rule-based signatures (exact metric/log patterns) and vector similarity (semantic log patterns). Results ranked by confidence and recency.

3. Inline context in the ticket

Top 3 matches rendered directly in the ticket view: root cause, resolution steps, prevention actions, and the engineer who resolved it. One click copies the resolution as a draft comment.

4. Feedback loop

On ticket close, the engineer confirms or corrects the matched pattern. Corrections retrain the matching weights. The library improves with every ticket.

Solution

A production service deployed as a sidecar to the existing ServiceNow/Jira workflow:

  • Ingestion pipeline: Scheduled jobs pull tickets, enrich with monitoring data (Prometheus, Loki, Elasticsearch), generate fingerprints, store in PostgreSQL + Elasticsearch.
  • Matching engine: FastAPI service exposing /match endpoint. Rule engine (YAML-defined signatures) + vector search (sentence-transformers, 384-dim) for semantic fallback.
  • UI widget: React component embedded in the ticket detail view via iframe. Shows matches, confidence, one-click resolution copy.
  • Learning loop: Closed-ticket feedback updates signature weights and vector index incrementally.
Context: Built for a 50-service production environment, ~200 engineers across L1/L2/L3 tiers. Integrated with existing monitoring stack (Prometheus, Grafana, Loki, Elasticsearch) and ticketing (ServiceNow).

The repeat-ticket rate dropped 68% within 8 weeks of rollout. Engineers stopped re-diagnosing known patterns and started closing tickets with "matched incident #1247 — applied resolution." The system became the default first step in the runbook.

What Went Wrong

  • Over-indexed on vector search initially. The first version used only embeddings. Precision was ~45%. Adding deterministic rule-based signatures (exact metric thresholds, log regexes) pushed it to 78% top-3. Lesson: structure beats semantics for operational patterns.
  • Didn't involve L1 engineers early enough. Built the matching engine in isolation. When deployed, L1s ignored it because it surfaced "obvious" matches they already knew. We added a "novelty score" — only show matches the current engineer hasn't seen — and adoption jumped.
  • Schema drift broke fingerprints. Monitoring metric names changed (e.g., cpu_usage → cpu.utilization) and fingerprints silently degraded. Added a schema registry with alerts on drift.
  • No offline mode. When the matching service was down, engineers had no fallback. Added a local cache of recent patterns in the UI widget.
